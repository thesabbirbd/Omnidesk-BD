## 2025-03-01 - DOMPurify usage for XSS mitigation in StreamingMessage
**Vulnerability:** A Cross-Site Scripting (XSS) vulnerability was present in the `StreamingMessage` React component due to the unsafe use of `dangerouslySetInnerHTML`. The component took AI-generated or user-controlled text, parsed it as Markdown (via string replacement), and injected it directly into the DOM without sanitization.
**Learning:** React's `dangerouslySetInnerHTML` is aptly named—it bypasses React's built-in escaping mechanisms. If untrusted input is passed to it, malicious scripts can execute in the victim's browser. While custom markdown renderers can parse text, they do not inherently strip malicious HTML tags or script attributes.
**Prevention:** Always use a reputable sanitization library, such as `DOMPurify`, to sanitize any HTML string before passing it to `dangerouslySetInnerHTML`. In this case, `DOMPurify.sanitize(renderMarkdown(displayedText))` ensures that only safe, expected HTML elements and attributes are rendered, effectively neutralizing XSS payloads.

## 2025-03-02 - Overly Permissive CORS Policy Mitigation
**Vulnerability:** The backend configuration allowed overly permissive Cross-Origin Resource Sharing (CORS) by setting `BACKEND_CORS_ORIGINS` to `["*"]` by default. This allowed any external website to make requests to the API, potentially exposing sensitive data to unauthorized domains.
**Learning:** Defaulting to wildcard (`*`) for CORS origins creates a significant risk by relaxing the same-origin policy, an essential browser security mechanism. CORS configurations should adhere to the principle of least privilege, explicitly listing only trusted domains.
**Prevention:** Always default CORS origin lists to an empty array (e.g., `[]`) or a restrictive set of known safe origins in the default configuration. Allow deployment environments to explicitly override this restrictive default via environment variables when necessary.

## 2025-03-01 - Hardcoded Refresh Secret Key in Configuration
**Vulnerability:** A hardcoded `REFRESH_SECRET_KEY` was present in `backend/app/core/config.py`. Because the default value was provided directly in the code, it could be exposed to anyone with access to the source code, posing a severe security risk by allowing unauthorized minting of valid refresh tokens.
**Learning:** Using Pydantic `BaseSettings` for configuration allows values to be easily read from environment variables. If a default fallback value is provided for a sensitive secret, the application will silently load that default when the environment variable is omitted. This circumvents the requirement for operators to securely provide the secret at deployment time.
**Prevention:** Never hardcode sensitive values (like API keys, secret keys, or cryptographic seeds) directly in source code. When using configuration management tools like Pydantic, define the sensitive field as a required type without a default value (e.g., `REFRESH_SECRET_KEY: str` instead of `REFRESH_SECRET_KEY: str = "default_value"`). This enforces a fail-closed posture: the application will refuse to start unless a secret is explicitly provided via environment variables, ensuring that default values cannot be accidentally used in production.

## 2025-03-01 - Hardcoded Secret Key in Configuration
**Vulnerability:** A hardcoded secret key was present in the `Settings` class of the FastAPI configuration (`backend/app/core/config.py`). This key is used to sign JSON Web Tokens (JWTs) for authentication. If exposed, an attacker could forge valid JWTs, impersonate any user, and gain unauthorized access to the application.
**Learning:** Hardcoding secrets directly in the source code is a significant security risk. Source code is often stored in version control systems, shared among developers, and may inadvertently be exposed. Secrets must be decoupled from the codebase and loaded from the environment at runtime.
**Prevention:** Always use environment variables to store sensitive configuration values such as secret keys, database credentials, and API tokens. In Pydantic-based FastAPI applications, this is achieved by defining the setting fields without default values (e.g., `SECRET_KEY: str`) or with a default of `None`, forcing the application to read them from the environment or a `.env` file via `BaseSettings`.
